# 明确异步请求与可靠投递的责任

保留提交异步请求、另外订阅结果的模式，本轮不增加同步等待结果的 RPC 接口。发布成功要求收到 broker 确认，并明确反馈无法路由的消息；确认丢失时返回发布结果未知，由调用方决定是否使用同一消息 ID 重试。

允许重复投递，业务处理器负责幂等；库提供稳定消息 ID、重投递信息和扩展入口，不承诺业务恰好执行一次。相比隐式重试或将发送返回视作业务成功，这一选择暴露不确定性，以避免错误的可靠性承诺。

暂时性错误有限重试，永久性错误及重试耗尽进入死信队列，默认禁止无限立即重入队。业务成功但结果发送失败时，基础模式允许重新投递请求并再次调用业务处理器；业务必须保证副作用幂等，并能返回同一请求的结果，而非仅跳过重复请求。需要数据库事务保证的场景由业务侧接入 outbox，库不隐式引入数据库。

普通错误和 panic 默认可重试；解码失败、协议不支持及显式永久错误不重试。默认首次处理失败后额外重试三次，间隔为 1 秒、10 秒、60 秒，允许按订阅覆盖；停机取消不计为业务失败。默认不保证业务处理顺序，即使并发度为 1，延迟重试仍可能改变完成顺序。

需要结果的请求在成功、永久失败或重试耗尽后产生相应结果，失败结果包含稳定错误码及安全的错误说明；死信用于另行排查。单向请求和事件不产生业务结果，结果通知失败也须恢复。
