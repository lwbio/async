# 异步消息库架构重设计

状态：已确认并实施。ADR 0001–0007 记录设计约束；具体使用方式见 README、protocol.md 和 operations.md，验证结果见 validation.md。

## 目标与范围

构建 RabbitMQ 专用 Go 库，全面使用新协议，优先解决可靠投递、断线恢复、有界消费和优雅退出。支持异步请求及结果通知、单向请求、事件订阅、JSON/protobuf 编解码、可选延迟请求、OpenTelemetry 和 protobuf 代码生成。

不提供同步等待结果的 RPC，不承诺恰好一次业务执行、默认顺序或旧协议兼容。不在库内引入业务数据库；数据库事务与 outbox 由业务集成。

## 重构前的问题

- 请求和事件消费均无条件确认消息，业务失败及结果发布失败可能失去恢复机会。
- 连接重建未形成完整的 channel、拓扑和消费者恢复流程。
- 消费循环无界创建 goroutine，取消不能可靠唤醒阻塞等待，退出不等待在途处理。
- 发布缺少 confirms 与 Return 的联合判定；事件标识只使用 enum 数字会发生跨类型冲突。
- 生成器与运行时协议紧耦合，追踪尚未覆盖请求及结果全链路。

## 模块划分

| 位置 | 职责 |
| --- | --- |
| 根包 `async` | `Runtime` 生命周期、配置、公共消息元数据与错误分类 |
| `request/` | 提交请求、注册处理器、接收结果；取代现有 `async/` 业务实现 |
| `pubsub/` | 事件发布与订阅、事件类型及订阅身份 |
| `internal/transport/` | 连接恢复、channel 代际、发布确认与 Return 配对 |
| 根包 `consumer.go` | 有界调度、确认、失败转移及退出 |
| `internal/topology/` | 队列、exchange、绑定和重试拓扑的声明及验证 |
| `internal/protocol/` | 新协议编码、校验、结果 ID 派生规则 |
| `encoding/`、`tracing/` | 编解码与追踪实现，经统一运行时接入 |
| `cmd/protoc-gen-go-async/` | 生成服务注册、类型化请求提交与结果解码代码 |

上层模块复用运行时行为，不持有原始 AMQP channel。内部只在确有替换或故障注入需要的位置设置小接口，不构造跨消息系统抽象。

## 对外使用流程

1. 创建 Runtime，配置地址、命名空间及可选能力；注册请求处理器、事件和结果订阅。
2. `Start(ctx)` 建立连接、验证并声明拓扑、启动消费者，成功后进入 Ready。
3. 请求客户端提交请求，返回请求 ID 和发布结果；事件发布使用同一确认机制。
4. `Stop(ctx)` 按调用方期限排空消费并关闭资源；重复停止安全，关闭前尚未启动也安全。

注册默认在启动前完成，以避免运行中拓扑与恢复清单并发变更。发布方可以单独启动 Runtime。默认并发度 8、prefetch 16，可按订阅覆盖；这些是资源默认值，不是性能承诺。

## 消息协议

协议包含版本、种类（请求／结果／事件）、消息 ID、关联 ID、完整操作或事件名称、结果目标、内容类型、重试次数、追踪上下文及负载。以 AMQP properties 和有命名空间的 headers 承载元数据，负载使用声明的 codec；具体字段映射见 protocol.md，协议样例与生成绑定均有测试。

- 请求及事件首次发布生成 MessageID，调用方可以提供既有 ID；重试不改变它。
- 结果使用独立且可重复派生的 MessageID，CorrelationID 指向原请求；同一请求的结果重发可去重。
- 请求没有结果目标时为单向请求；有目标时产生成功或失败结果。
- 失败结果携带稳定错误码及安全说明，不暴露原始堆栈或连接凭据。
- 未知版本、非法元数据及解码失败属于永久错误；无法取得可信回复目标的畸形请求只进入死信处理。

完整事件名包含 protobuf 类型及枚举值名称，不以枚举数字单独作为身份。

## 订阅与拓扑

订阅名默认从处理器所属包和函数或方法名生成，允许覆盖；命名空间隔离不同应用环境。相同订阅映射到相同队列并竞争消费，不同订阅分别接收事件。匿名函数及闭包可能共享身份，重命名可能生成新队列，接受这些自动命名限制。

生成器须传递业务处理器身份，不能让所有订阅被同一个生成包装函数识别。绑定和消费配置须对同一订阅一致；可检查的冲突在启动时报告。

可靠路径使用持久化 quorum 业务队列、独立的 1 秒／10 秒／60 秒重试队列和死信队列，消息持久化。每个 DLX 转发源启用 `dead-letter-strategy=at-least-once`、`overflow=reject-publish` 及对应 DLX。基础设施 policy 及必要 feature flag 纳入部署检查；不自动修改整个集群的策略。

重试队列绑定回原订阅，不能把一次订阅重试重新广播给所有订阅。TTL 是最早可重投的延迟，不是精确定时保证。结果队列须先建立；请求提交成功不代表结果接收方一直在线。

旧协议不兼容；新拓扑使用独立协议命名空间，已有消息由部署方决定排空或另行处置，库不自动删除旧队列。

## 发布与消费确认

普通发布使用 confirms 与 mandatory，联合处理 Return；broker ACK 单独不足以判定可路由。结果分为成功、明确失败、结果未知；在途发布数有界，等待尊重调用上下文。已发送后取消或断线可能返回结果未知，不能伪装成确定未投递。

每个发布 channel 使用单条在途确认发布，避免 Return 与消息错配。默认一个 channel，可通过 `Config.PublishConcurrency` 显式配置 1–32 条有界并行发布 channel；每条独立配对 Return/confirm，不改变发布结果语义，也不提供跨 channel 顺序。

| 消费结果 | 处理 |
| --- | --- |
| 事件或单向请求成功 | ACK 原消息 |
| 需要结果的请求成功 | 确认结果发布成功，再 ACK 请求 |
| 可重试业务错误或 panic | 确认发布到对应重试队列，再 ACK 原消息 |
| 永久错误或业务重试耗尽 | 必要时发布失败结果，并确认死信转移后 ACK 原消息 |
| 转移或结果发布失败／结果未知 | 保留恢复机会，不当作已完成消息确认 |
| 停机取消 | 不增加业务失败次数，未完成消息留待重新投递 |

业务默认额外重试三次，间隔为 1／10／60 秒，可按订阅覆盖。明确的基础设施转移失败只暂停对应订阅、关闭其消费 channel 并按 1–30 秒指数退避恢复；成功处理后重置退避。ACK/channel 故障和 broker 取消也使用同一局部恢复路径；网络或发布确认不确定仍触发连接级恢复。不因业务重试预算耗尽而丢弃原消息。基础设施故障及确认间隙可能造成额外重复调用，次数上限不代表业务处理器最多执行四次。

结果确认与请求 ACK、失败结果发布与死信转移均非原子操作，故障可能产生重复。业务必须对原请求保持幂等并返回一致结果；结果接收方也须去重。结果消息的处理失败不会再生成“结果的结果”。

## 恢复与退出

状态为 Created → Starting → Ready；故障进入 Recovering，恢复后回到 Ready；停止进入 Draining → Closed。停止优先于重连，Closed 不再自动启动。

每次连接使用新的关闭通知 channel。连接代际变化时，旧 channel、消费者及未完成确认统一失效；重建拓扑、QoS、订阅及 Return/confirm 监听后才报告 Ready。发布 channel 和消费 channel 分离，避免消费控制影响发布确认。

断线期间新发布返回不可用，不建立无限内存缓冲。停止先取消消费接收并处理已经交付的消息，再等待工作完成；期限耗尽取消 handler 上下文、关闭 channel。库不能强制终止不响应取消的业务 goroutine。

## 可选延迟与可观测性

延迟 exchange 显式启用，单独暴露能力限制：插件不支持 mandatory，延迟消息单节点存储。其发布确认不表示到期时可路由，不纳入普通路径的同等级可靠承诺。

所有路径统一注入和提取追踪上下文，panic 和业务错误正确结束 span；记录重连、未知发布结果、失败转移、重试、死信及在途数量。日志包含消息与订阅身份，默认不记录负载和凭据。

## 实施顺序与验收

1. 固定协议字段和样例、整理当前未完成接口，建立可编译基线，保留已有工作区修改。
2. 实现运行时状态机与确认发布；验证 Return/ACK 顺序、确认丢失、重复关闭和重连竞态。
3. 实现有界消费与重试拓扑；验证 handler 错误、panic、结果发布失败、目标不可用及 ACK 间隙故障。
4. 接入请求、事件、结果与 codec；验证稳定 ID、事件身份冲突、自动订阅名与覆盖行为。
5. 更新生成器并编译生成样例；接入追踪、可选延迟及部署文档。

根模块及生成器模块分别执行 build、test、vet；并发逻辑执行 race 检查。真实 RabbitMQ 集成测试必须验证重启、连接切断、消费者恢复、重试路由隔离及退出期限。Quorum 少数／多数副本失效的保证通过多节点测试验证，不能用单节点单测替代。

已固定 RabbitMQ 4.2 验证基线并记录部署要求；CI 的 Go 版本从 go.mod 读取。只有实际执行并通过的检查才能报告为已验证。
